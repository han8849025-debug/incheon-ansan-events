# Remote Control MCP (안끊김) 연결 끊김 허점 정리

(구글 Docs 원본을 그대로 옮긴 사본. 원본: https://docs.google.com/document/d/1W-ziiyJOZ2PkRIZKS8Ir5XkrOfeIIiOA1ZRb67-RN50/edit)

작성일: 2026-11-07. 대상: 개조판 앱 Remote Control MCP (안끊김), 패키지 com.danielealbano.androidremotecontrolmcp.keepalive, 버전 1.12.0 (필립이 올린 APK 기준, 이 폴더의 RemoteControlMCP-keepalive.apk). 근거: APK 코드 분석, 폰 Server Logs 캡처 1장(2026-11-07 11:43), UptimeRobot 알림 메일(2026-10-16부터 10-20까지). 시각은 모두 한국 시간입니다.

## 읽는 법

각 항목에 근거 수준을 붙였습니다. 확인됨은 APK 코드에서 직접 읽은 내용, 추정은 로그나 알림 메일을 코드와 맞춰 본 해석, 미확인은 아직 보지 못한 부분입니다.

## 요약

개조판에는 15초마다 터널 상태를 점검하고, 하트비트가 끊기면 터널을 재시작하는 감시(ConnectionKeeper)가 들어 있습니다. 이 감시 자체가 멈추는 경로가 코드에 있고, 11월 7일 로그가 그 경로와 맞아떨어집니다. 다만 ngrok 연결 닫기가 실제로 멈췄는지는 확인하지 못했습니다.

## A. 코드에서 확인된 허점

1. **재시작 호출에 제한 시간이 없음 (확인됨)**: 감시 루프(ConnectionKeeper.runWatchdog)는 15초 점검에는 제한 시간(15초)을 쓰지만, 재시작(TunnelManager.restart)은 끝날 때까지 무한정 기다립니다. 재시작이 멈추면 감시 루프도 같이 멈춥니다.
2. **터널 정지가 잠금을 잡은 채 연결 닫기를 기다림 (확인됨)**: TunnelManager.stop은 잠금(Mutex)을 잡은 상태에서 NgrokTunnelProvider.stop을 부르고, 그 안에서 ngrok 세션 닫기를 제한 시간 없이 기다립니다. 닫기가 끝나지 않으면 잠금이 풀리지 않아, 이후의 모든 터널 시작과 정지 호출이 대기 상태로 남습니다.
3. **"Tunnel stopped" 로그가 닫기 전에 찍힘 (확인됨)**: 정지 로그는 ngrok 세션 닫기를 시작하기 전에 기록됩니다. 로그에 "Tunnel stopped"가 있어도 닫기가 끝났다는 뜻이 아니므로, 진단할 때 정상 정지로 오해할 수 있습니다.
4. **감시 루프가 멈추면 웨이크락 갱신도 멈춤 (확인됨)**: 웨이크락 갱신(renewWakeLock)은 감시 루프가 한 바퀴 돌 때마다 실행되고, 웨이크락의 최대 유지 시간은 1시간입니다. 루프가 멈추면 갱신이 끊겨 약 1시간 뒤 웨이크락이 만료됩니다.
5. **하트비트를 한 번도 못 받은 연결은 정상으로 판정 (확인됨)**: NgrokTunnelProvider는 하트비트를 한 번 이상 받아야 마지막 하트비트 시각을 돌려주고, 아니면 null입니다. 감시 정책(WatchdogPolicy)은 상태가 Connected이고 시각이 null이면 정상으로 처리합니다. 터널이 "연결됨"으로 표시되지만 실제로 통하지 않는 상태가 감시에 잡히지 않을 수 있습니다.
6. **판정 입력이 세 가지뿐 (확인됨)**: 감시의 판정 함수(WatchdogPolicy.decide)는 터널 상태, 마지막 하트비트 시각, 네트워크 유무만 입력으로 받습니다. 바깥에서 실제로 접속이 되는지는 확인하지 않습니다.
7. **감시가 앱 프로세스 안에서만 동작 (확인됨, 일부 미확인)**: 감시 루프는 앱 프로세스 안의 코루틴이어서, 프로세스가 종료되면 감시도 함께 사라집니다. ConnectionKeeper 안에서 앱 밖에서 되살리는 알람이나 작업 예약은 찾지 못했습니다. 부팅 후 시작(BootCompletedReceiver)과 앱 업데이트 후 시작(PackageReplacedReceiver)은 있으나, 프로세스가 중간에 죽었을 때 되살리는 경로는 확인하지 못했습니다.
8. **복구 속도의 구조적 한계 (확인됨)**: 하트비트가 75초를 넘게 없어야 이상으로 판정하고, 연결 중 상태가 60초를 넘게 이어져도 이상으로 봅니다. 점검 주기는 15초이고, 재시작이 실패하면 대기 시간이 5초에서 최대 120초까지 늘어납니다. 정상적으로 동작해도 끊김이 수 분 이어질 수 있습니다.

## B. 로그와 알림 메일에서 나온 정황

1. **11월 7일 09:55:20 재시작이 정지에서 끝남 (추정)**: 09:54:09에는 "Tunnel stopped" 직후 "Tunnel connecting…"이 찍혔습니다. 반면 09:55:20에는 "Watchdog: restarting tunnel (no heartbeat for 35s)"와 "Tunnel stopped"만 찍히고 "연결 중"이 이어지지 않았습니다.
2. **09:55 이후 11:28까지 감시 로그가 없음 (추정)**: 약 1시간 33분 동안 감시 관련 로그가 한 줄도 없다가, 11:28:19에 "no heartbeat for 3584s"(약 1시간)가 기록됐습니다. 감시가 이 시간 동안 멈춰 있었다고 보면 앞뒤가 맞습니다. 확정된 사실은 아닙니다.
3. **11:28:19 재시작 이후에도 로그가 없음 (추정)**: 서버가 11:28:10부터 11:28:14 사이에 정지 후 재시작됐고, 11:28:19에 새 감시가 "restarting tunnel"을 기록했습니다. 그 뒤 "Tunnel stopped"나 "connecting"은 캡처 시각 11:43까지 없습니다. 항목 2의 잠금에 막힌 상태와 맞습니다.
4. **알림 메일의 끊김 기간이 설계상 복구 시간보다 긺 (추정)**: 2026-10-16부터 10-20까지 UptimeRobot 끊김 알림이 8회 있었고, 기간은 5분에서 67분까지입니다(최장은 10-20 17:46부터 18:53까지). 설계상 복구는 길어야 수 분인데 20분 이상 끊긴 사례가 여럿이라, 그때 감시가 동작하지 않았을 가능성이 있습니다. 10-20 이후 확인 시점까지 새 알림은 없었고, 11-07 오전 끊김은 알림 메일에서 확인하지 못했습니다.

## C. 설정과 환경

1. **앱 알림이 꺼져 있음 (필립 설정)**: 알림창으로는 앱이 살아 있는지 확인할 수 없어, 앱 안의 Server Logs 화면으로 확인해야 합니다.
2. **삼성 절전과 앱 정지 가능성 (미확인)**: 폰이 백그라운드 앱을 얼리거나 종료했는지는 확인하지 못했습니다. 끊긴 직후의 앱 상태와 로그 말고는 확인 수단이 없습니다.
3. **ngrok 무료 터널 사용 (확인됨)**: 로그의 연결 주소가 ngrok-free.dev 도메인이고, 재시작 뒤에도 같은 주소로 다시 붙습니다.
4. **ngrok 라이브러리의 자동 재연결과 앱의 재시작이 겹칠 가능성 (추정)**: 하트비트가 시간 초과되면 ngrok 라이브러리가 스스로 재연결을 시도하는 구조입니다(코드 로그 문구 "library will reconnect"). 같은 시점에 앱의 감시도 터널을 재시작하므로 두 동작이 겹쳐 상태가 어긋날 수 있습니다.

## D. 풀리지 않은 불일치

1. **로그의 35초와 APK의 75초가 맞지 않음**: 11월 7일 09:55:20 로그는 하트비트 없음 35초에 재시작을 기록했는데, 올려준 APK 코드는 75초를 넘어야 재시작합니다. 폰에 깔린 개조판이 이 APK와 다른 빌드일 수 있습니다. 폰 앱의 About 화면 버전으로 확인할 수 있고, 올려준 APK는 1.12.0입니다.

## E. 아직 읽지 않은 부분 (서비스, 수신기, Cloudflare는 I에서 읽음)

- McpServerService: 서버 서비스 본체와 시작 과정
- BootCompletedReceiver, PackageReplacedReceiver: 자동 시작 조건
- McpServerRestartKt: 서버 재시작 도우미 (디컴파일만 하고 내용은 읽지 않음)
- CloudflareTunnelProvider: Cloudflare 방식의 감시 (필립은 ngrok 사용 중)
- ngrok 라이브러리 내부: 네이티브 코드라 읽지 못함
- 감시 루프 본문: 바이트코드로만 확인했고 소스 형태의 디컴파일은 실패함

## F. 검토했지만 해당하지 않는 항목

- Cloudflare 터널의 감시 부족: 필립은 ngrok을 쓰고 있어 해당하지 않습니다.
- 재시작 뒤 외부 주소 변경: ngrok 고정 도메인이라 같은 주소로 다시 접속합니다.
- 와이파이와 모바일 데이터 전환: 로그에 전환 흔적이 없습니다.

## G. 개선 방향

앱을 고칠 수 있게 되면 다음 순서로 손보는 것이 좋습니다.

1. 재시작과 터널 정지에 제한 시간을 걸고, 시간이 지나면 잠금을 반드시 해제합니다.
2. ngrok 세션 닫기를 끝까지 기다리지 않고, 제한 시간 뒤에는 포기하고 새 세션을 만듭니다.
3. 하트비트를 처음부터 받지 못한 연결도 일정 시간이 지나면 이상으로 판정합니다.
4. 점검 루프를 터널 재시작과 분리해, 재시작이 멈춰도 점검이 계속 돌게 합니다.
5. 바깥에서 실제로 접속이 되는지 확인하는 점검을 추가합니다.
6. 재시작의 각 단계(정지 시작, 정지 완료, 시작 시도, 연결 완료)를 로그로 남깁니다.
7. 앱 밖에서 프로세스가 살아 있는지 확인하고 되살리는 장치를 검토합니다.

## I. 추가로 읽은 코드에서 나온 내용 (2026-11-07)

E에 적었던 부분 중 서버 서비스, 부팅 수신기, 서버 재시작 도우미, Cloudflare 터널을 읽었습니다. ngrok 라이브러리 내부는 네이티브 코드라 여전히 읽지 못했습니다. 번호 표기는 A의 항목 번호를 뜻합니다.

- **서비스는 시스템이 종료해도 다시 시작되도록 설정됨 (확인됨)**: McpServerService.onStartCommand는 정지 요청이 아닌 경우 START_STICKY를 돌려줍니다. 시스템이 서비스를 종료하면 서버를 다시 켜고, 앱 목록에서 앱을 밀어서 지운 경우(onTaskRemoved)에도 서버가 실행 중이었으면 다시 시작을 요청합니다. 그래서 A의 7번에서 "되살리는 경로를 못 찾았다"고 적은 부분은 일부 정정합니다. 다만 이 함수는 디컴파일 결과가 불완전해서 값 해석에 오차가 있을 수 있습니다.
- **백그라운드에서의 재시작 실패가 화면 로그에 남지 않음 (확인됨)**: 앱이 배터리 최적화 예외가 아니면 백그라운드에서 서비스를 시작하는 것이 막힐 수 있습니다(ForegroundServiceStartNotAllowedException). 코드는 이 예외를 삼키고 안드로이드 시스템 로그에만 경고로 남깁니다. 앱 안의 Server Logs 화면에는 나타나지 않습니다.
- **부팅 후 자동 시작은 설정에 달려 있음 (확인됨)**: BootCompletedReceiver는 부팅 알림을 받으면 설정을 최대 10초 동안 읽고, 자동 시작이 켜져 있을 때만 서버를 시작합니다. 필립 폰의 이 설정은 확인하지 못했습니다. PackageReplacedReceiver도 같은 구조로 보입니다.
- **터널 관리자는 앱 프로세스 안에 하나만 존재 (확인됨)**: TunnelManager는 싱글턴이라, 서버를 껐다 켜도 같은 객체와 같은 잠금(Mutex)이 이어집니다. A의 2번처럼 잠금이 풀리지 않은 채 남았다면, 앱 안에서 서버를 껐다 켜는 것만으로는 풀리지 않을 수 있습니다.
- **서비스 종료 때는 터널 정지를 3초만 기다림 (확인됨)**: McpServerService.onDestroy는 터널 정지를 최대 3000ms까지만 기다립니다("Tunnel stop timed out after 3000ms" 문구). 이 대기는 runBlocking이라 화면 스레드를 최대 3초 막습니다. 반면 감시의 재시작 호출(A의 1번)에는 제한이 없습니다.
- **11월 7일 11:28 로그의 3초 간격이 이 제한과 일치 (추정)**: "Server stopping"(11:28:10)부터 "Server stopped"(11:28:13)까지가 3초이고, 그 사이에 "Tunnel stopped" 로그가 없습니다. 정지 호출이 3초 제한까지 막혀 있었다는 해석과 맞고, A의 2번 가설에 증거가 하나 더해집니다.
- **Cloudflare 터널에는 하트비트가 구현되어 있지 않음 (확인됨)**: CloudflareTunnelProvider는 마지막 하트비트 시각을 따로 구현하지 않습니다. 필립은 ngrok을 쓰므로 직접 영향은 없습니다. 참고로 Cloudflare의 정지는 5초 제한과 프로세스 강제 종료로 막히지 않게 되어 있고, ngrok의 정지에는 이런 제한이 없습니다.
- **서버 시작 순서와 맞지 않는 부분이 남아 있음 (미해결)**: startServer는 터널 시작(TunnelManager.start)이 끝나야 새 감시를 만듭니다. TunnelManager.start도 같은 잠금을 쓰므로, 잠금이 풀리지 않았다면 새 감시가 만들어지지 않아야 합니다. 그런데 11월 7일 11:28:19에는 새 감시가 동작한 기록이 있습니다. 잠금 가설은 이 불일치 때문에 아직 확정할 수 없습니다.
- **지금 단계의 결론과 임시 대처 (추정)**: 재시작이나 정지가 끝나지 않는 문제가 유력하지만 확정은 아닙니다. 확정하려면 재시작의 각 단계와 잠금 획득과 해제를 로그로 남기는 개조가 필요합니다. 임시 대처로는 앱을 강제 종료한 뒤 다시 여는 방법이 위 내용과 맞지만, 효과는 아직 시험하지 못했습니다.
